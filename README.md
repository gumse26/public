# gate.atol.piot

Шлюз ККТ АТОЛ (ФФД 1.2) через **внешнюю компоненту 1С** — вариант, при котором работа с
кассой идёт не через COM-объект драйвера, а через компоненту `fptr10_1c_win32_….dll`,
подключаемую платформой 1С.

Компонента — обычная DLL с интерфейсом Native API (экспорты `GetClassNames`,
`GetClassObject`, `DestroyObject`, `SetPlatformCapabilities`). Чтобы вызывать её методы
без 1С, нужен хост — он здесь и лежит (`gate.1c.addin.proxy.exe`), а шлюз `gate.atol.piot.exe`
разговаривает с хостом по JSON-RPC и предоставляет удобный слой: внешний протокол,
XML по требованиям, веб-форму настроек.

## Что в репозитории

| Файл | Что это |
|---|---|
| `gate.atol.piot.exe` | шлюз, single-file (~240 КБ) — один файл, без DLL рядом; нужен установленный рантайм **.NET 8 или новее** |
| `gate.1c.addin.proxy.exe` | хост внешней компоненты 1С, **x86** |
| `atol.settings.html` | веб-форма настроек оборудования (её отдаёт шлюз) |
| `config.json`, `config.example.json` | настройки шлюза |
| `settings.json` | стартовые значения параметров оборудования |
| `1_settings_form.bat` | поднять хост + сервис настроек и открыть форму |
| `2_gateway_queue.bat` | рабочий режим: очередь GATE |
| `3_selftest.bat` | автотест с реальным подключением к кассе |
| `4_remote_agent.bat` | запуск агента удалённого обслуживания — **подставьте свою очередь и токен** |
| `remote_agent.exe` | агент удалённого обслуживания рабочего каталога, **x86** |
| `docs/` | примеры JSON-запросов и ответов: по файлу на каждый вид операции, с описанием полей |

**Компонента АТОЛ в репозитории отсутствует** — `fptr10_1c_win32_10_10_8_21.dll`
поставляется в составе драйвера АТОЛ «ДТО 10» и публикации не подлежит. Положите её
рядом с `gate.1c.addin.proxy.exe` (см. ниже).

## Что нужно на машине

1. **Windows x64.**
2. **Установленный драйвер АТОЛ «ДТО 10»** — он даёт `fptr10.dll`
   (обычно `C:\Program Files (x86)\ATOL\Drivers10\KKT\bin\`). Именно этот драйвер
   общается с кассой; без него компонента не подключится.
3. **Файл компоненты** `fptr10_1c_win32_10_10_8_21.dll` — возьмите его из поставки
   АТОЛ (в комплекте «Технология создания внешних компонент» / ДТО 10) и положите
   рядом с `gate.1c.addin.proxy.exe`.
4. **ККТ, подключённая к машине.** Если касса на USB, она обычно видна как
   виртуальный COM-порт (`atol-usbcom_proxy`); при первом запуске формы проверьте
   `Port` и `ComFile` под свою конфигурацию.
5. Свободные порты **8082** (хост компоненты) и **8083** (сервис настроек).
6. Права на запуск exe из этой папки. Если появляется
   *«This program is blocked by group policy»* — папку нужно добавить в исключения
   групповых политик (SRP/AppLocker); это ограничение среды, а не программы.

**.NET нужен — только рантайм, не SDK.** Шлюз собран как single-file (framework-dependent):
один exe и никаких DLL рядом, но на машине должен быть установлен рантайм **.NET 8 или
новее** (проверено на 8.0.12 и 10.0.11 — в сборке `RollForward=LatestMajor`).
Проверить: `dotnet --list-runtimes`.

## Быстрый старт

```bat
:: 1. отредактируйте config.json: gate, queue, cashier_name, sale_address, sale_location
:: 2. поднимите форму настроек
1_settings_form.bat
```

Откроется <http://127.0.0.1:8083/>. В форме:

* **Загрузить из шлюза** — подтянуть значения из `settings.json`;
* **Проверить на ККТ** — реально подключиться и увидеть данные кассы
  (серийный номер, ФН, ОФД, СНО) либо текст ошибки;
* **Сохранить** — записать значения в `settings.json`;
* **Сформировать XML** / **Копировать** — собрать XML для метода
  `ПодключитьОборудование`.

Затем:

```bat
3_selftest.bat          :: проверка хоста, подключения и методов
2_gateway_queue.bat     :: рабочий режим
```

## Настройки шлюза (`config.json`)

| Поле | Значение |
|---|---|
| `gate` | адрес сервера очередей GATE |
| `queue` | имя очереди, которую слушает шлюз |
| `addin` | адрес хоста компоненты (`http://127.0.0.1:8082/rpc`) |
| `cashier_name` | ФИО кассира — обязательный атрибут `CashierName` в чеке |
| `sale_address`, `sale_location` | адрес и место расчётов для чека |
| `taxation_system` | СНО: `0` — Общая, `1` — УСН Доход, `2` — УСН Доход-Расход, `3` — ЕНВД, `4` — ЕСХН, `5` — Патент |
| `equipment_type` | тип оборудования, по умолчанию `ККТ` |
| `settings_file` | файл настроек оборудования |
| `http_port` | порт сервиса настроек; `0` — не поднимать (переопределяется ключом `--http`) |

## Предохранители

По умолчанию:

```json
"dry_run": true,
"allow_fiscal": false
```

* `dry_run: true` — шлюз **ничего не отправляет** в кассу: собирает XML, проверяет
  инварианты и пишет журнал. Режим безопасной обкатки на незнакомом стенде.
* `allow_fiscal: false` — фискальные операции (чеки, закрытие смены) отклоняются
  даже при `dry_run=false`.

Для реальной работы снимите оба: ключами `--no-dry-run --allow-fiscal` или правкой
`config.json`. Это фискальные документы — включайте осознанно.

## Ключи командной строки

```

```

## Сервис настроек (API)

Слушает только `127.0.0.1`.

| Метод | Назначение |
|---|---|
| `GET /` | форма `atol.settings.html` |
| `GET /api/settings` | сохранённые значения + собранный `connectXml` |
| `POST /api/settings` | сохранить значения (`{"values":{…}}`) |
| `GET /api/schema` | схема параметров с ККТ (при неудаче — кэш `settings-schema.xml`) |
| `GET /api/description` | `ПолучитьОписание` — версия драйвера и компоненты |
| `POST /api/check` | подключиться с переданными настройками и прочитать данные ККТ |

## Проверенные особенности компоненты

Собрано практикой на живой кассе АТОЛ (ФФД 1.2). Может сэкономить время:

1. **Компонента и хост — x86.** Менять на x64 можно только обе сразу; шлюзу
   разрядность безразлична — он общается с хостом по HTTP.
2. **`gate.1c.addin.proxy.exe` держит порт кассы.** Не запускайте два экземпляра и не держите
   хост, когда кассой работает 1С: порт будет занят.
3. **`ПодключитьОборудование` принимает полный XML настроек, но не применяет их.**
   Проверено: неверный `ComFile` не мешает подключению — драйвер подключается
   автоопределением. Параметры в `settings.json` — это описание оборудования,
   а не управление соединением.
4. **Для чеков с кодом маркировки проверка КМ и сам чек должны идти через один и тот
   же хендл устройства.** Иначе ККТ отвечает ошибкой `420 «Контрольная марка не
   проверена»`. В `config.json` хендл фиксируется полем `device`.
5. **Отраслевой реквизит позиции ККТ не возвращает.** Для чека с маркировкой его
   собирает вызывающая сторона: `AttributeValue="UUID=<GUID из ProcessingKMResult>&Time=<мс>"`,
   `IdentifierFOIV="030"`.
6. **Состояние «КМ проверена» живёт в рамках хендла.** Неподтверждённый `ЗапросКМ`
   оставляет процедуру открытой: следующий `ЗапросКМ` падает с ошибкой
   `401 «Процедура проверки КМ уже запущена»`, снимается методом
   `ЗакрытьСессиюРегистрацииКМ`.
7. **Результат проверки КМ приходит в ОИСМ, а не от ФН.** Метод `ЗапросКМ` отдаёт
   `RequestKMResult Checking="False" CheckingResult="False"` независимо от
   корректности кода — итог нужно забирать методом `ПолучитьРезультатыЗапросаКМ`.
   В `ResultCode` (тег 2106, таблица 110 ФФД) значение `15` = `1111b` — код проверен,
   КП положительный, статус ОИСМ проверен и корректен.
8. **Ставка НДС 22 % на части сборок компоненты не принимается** — приходит ошибка
   `26 «Неверный формат команды»`; проверка СНО выполняется раньше проверки позиций,
   поэтому при неверной СНО сначала приходит `143 «ККТ не зарегистрирована с указанной СНО»`.
9. **Метод `ПараметрыОборудования`** (2 параметра: `[{str: ИД}, {out: размер}]`)
   возвращает **схему** параметров с `DefaultValue`, без текущих значений.
